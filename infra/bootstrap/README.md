# Bootstrap

What GitHub Actions needs before it can authenticate, made inside blust.ch's project `blust-ch-mcp`, which ZITADEL shares with the MCP host that `robertblust/mcp-blust-ch` deploys: the APIs the other roots use, the state bucket `id-blust-ch-tfstate`, the identity pool `id-github` and its GitHub provider, the `id-deploy` and `id-deploy-plan` service accounts, and `zitadel` and `zitadel-login`, the accounts the two services run as. Every value it takes is read from `../../deployment.json`.

It makes no project, no budget and no organization policy. The project, its billing account and its one budget are mcp-blust-ch's, and that budget covers ZITADEL too. The override of the organization's domain-restricted sharing that the MCP host's public services need exists in the project already, from the shared bootstrap in `companygraph/mcp-server`, and ZITADEL needs none, since its services turn the invoker check off rather than grant `allUsers`. Each API it enables carries `disable_on_destroy = false`, as mcp-blust-ch's do, so destroying this root never turns off an API the MCP host uses.

Every name was checked against what mcp-blust-ch makes in the project, from the shared bootstrap at the release its `infra/bootstrap` pins and from its roots `infra` and `infra/chat`, and a name that would meet one of those carries `id-`. The pool is `id-github`, because the MCP host's is `github`; the provider inside it stays `github`, since a provider's id is scoped to its pool. The CI accounts are `id-deploy` and `id-deploy-plan`, because the MCP host's image pusher is `deploy@`, and the plan account takes the prefix too so the two read as a pair and as this repository's. The state bucket is named for the repository, because the project's name would give `blust-ch-mcp-tfstate`, the MCP host's own state. The custom role is `idSecretsWithoutAccess`, since a role's id takes no hyphen. The rest keep their names, because nothing of the MCP host's is called the same: the secrets `zitadel-*`, the Cloud SQL instance `zitadel`, the Cloud Run services and accounts `zitadel` and `zitadel-login`, and the load balancer's resources `id` and `id-redirect`. This repository has no image registry; its services run ZITADEL's own images.

The owner applies it, locally, under their own login, when the repository or the CI identities change; the Owner role on `blust-ch-mcp` covers everything it makes, and CI's own accounts hold none of the roles it needs. Its state is local and stays on the owner's machine, never in the bucket it creates, so a second copy of `terraform.tfstate` kept somewhere safe is the only backup it has. The state file is ignored by git and never committed.

The first apply has no state to restore. Every later one restores it first: copy `~/id-blust-ch-bootstrap.tfstate` to `infra/bootstrap/terraform.tfstate` before running anything. The plan that follows must not add the pool, the bucket or the service accounts — a plan that does means the state is missing rather than the infrastructure, so stop and find the copy before applying anything. Once the apply finishes, copy the state back out to the same file, and to the second safe copy.

    gcloud auth application-default login
    cp ~/id-blust-ch-bootstrap.tfstate infra/bootstrap/terraform.tfstate   # not on the first apply
    terraform -chdir=infra/bootstrap init
    terraform -chdir=infra/bootstrap plan
    terraform -chdir=infra/bootstrap apply
    cp infra/bootstrap/terraform.tfstate ~/id-blust-ch-bootstrap.tfstate

A run for a pull request plans as `id-deploy-plan@blust-ch-mcp.iam.gserviceaccount.com`, and only a push to `main` may apply, as `id-deploy@blust-ch-mcp.iam.gserviceaccount.com`; the bootstrap lets neither account be used the other way, and a run on `main` started by hand, on a schedule or by a comment gets neither. The pool accepts tokens from this repository alone, by its GitHub id, and no identity of the MCP host's names this pool, so no run of either repository becomes an identity of the other.

## What each identity reaches in the shared project

A role granted on the project reaches every resource of its kind there, the MCP host's as well as ZITADEL's, so each role is held to ZITADEL's resources wherever a condition can name them. Secret Manager and Cloud SQL accept a condition on the resource's name: Secret Manager names a secret by the project's number, `projects/38003987140/secrets/zitadel-*`, and Cloud SQL an instance by the project's id, `projects/blust-ch-mcp/instances/zitadel`. Cloud Run and IAM's service accounts accept none, and Compute Engine accepts one on only some of a load balancer's resources (https://docs.cloud.google.com/iam/docs/conditions-resource-attributes, read Oct 23, 2026). Making and listing are checked on the project, which carries no name, so each condition holds the name only for the resource types that carry one and lets the project through.

`id-deploy@` holds the Cloud Run administrator, the Compute Engine load balancer administrator and the service usage consumer on the project; `idSecretsWithoutAccess`, a Secret Manager role that makes secrets and sets their policies but reads no value, on secrets named `zitadel-*`; the Cloud SQL administrator on the instance `zitadel`; the project IAM administrator only for granting the Cloud SQL client role; the service account user on `zitadel@` and `zitadel-login@` alone; and the objects of the state bucket. It reads `zitadel-admin-key` by a grant on that secret alone in `../secrets.tf`. What it reaches of the MCP host is what no condition can hold: it could change, replace or delete the Cloud Run services `mcp` and `chat` and set who may invoke them, though any revision it deploys runs as `zitadel@` or `zitadel-login@`, the only accounts it may act as, never as `terraform@`, `chat-run@` or `mcp-run@`; it would administer any load balancer the project held, and the MCP host holds none, since Firebase Hosting fronts it; and it could grant the Cloud SQL client role to anyone, which reaches no instance of the MCP host's, since it has none. It can make a secret of any name, because making one is checked on the project, but cannot read, change or set the policy of any secret outside `zitadel-*`. It makes no service account, so it holds no role over any account in the project. Within ZITADEL it still has two ways to any other secret's value: setting a secret's policy is setting who reads it, so it could grant itself one, and with the Cloud Run administrator and the service account user on `zitadel@` it could deploy a revision that runs as `zitadel@` and reads that account's secrets. Every grant and service it makes is declared in `../` and recorded in the audit log, and only a push to `main` holds it.

`id-deploy-plan@` holds the Cloud Run viewer, the Compute Engine viewer, the security reviewer and the service usage consumer on the project; the Secret Manager viewer on secrets named `zitadel-*` and the Cloud SQL viewer on the instance `zitadel`; and the objects of the state bucket to read. The one secret value it reads is `zitadel-admin-key`, granted on that secret alone in `../secrets.tf`, because the `zitadel/` plan has to sign in to ZITADEL, and that key is the instance's IAM_OWNER. It holds no project viewer, because in a shared project the viewer reads the MCP host's logs, its Firestore meter and, through each bucket's default policy, which lets the project's viewers read objects, the MCP host's state and the chat's reports. What it still reads of the MCP host is the configuration of the services `mcp` and `chat`, through the Cloud Run viewer, and every IAM policy in the project, through the security reviewer; no value, no log and no object.

The MCP host's identities reach ZITADEL in turn, and the owner accepted that. `terraform@`, the shared bootstrap's apply identity, which a run on `main` of `robertblust/mcp-blust-ch` takes, holds the project IAM administrator without a condition, the Cloud Run administrator, the service account administrator and user, the storage administrator and the service usage administrator. So it reaches all of ZITADEL: it can grant itself any secret's value, the masterkey's included, deploy a revision as `zitadel@`, act as `id-deploy@`, read, replace or delete this repository's state, and turn off the APIs ZITADEL runs on. `terraform-plan@`, which a run on any ref there may take, holds the project's viewer and the security reviewer: it reads ZITADEL's configuration, its logs and every policy, and through the default policy of `id-blust-ch-tfstate` the state of `../` and `../../zitadel`, which holds no secret but does hold the owner's login name in the ZITADEL service's configuration; it reads no secret's value. `firebase-adminsdk-fbsvc@`, which Firebase made for the MCP host's hosting, holds the service account token creator on the project, so whoever may act as it, `terraform@` among them, may act as any account there, `zitadel@` and `id-deploy@` included. The MCP host's other accounts, its image pusher `deploy@`, `mcp-run@`, `chat-run@`, `chat-analyst@` and `kpi-reporter@`, hold nothing of ZITADEL's.
