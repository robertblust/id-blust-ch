# id.blust.ch

The family's own identity service, ZITADEL, at `https://id.blust.ch`. A reader signs in there once, on its hosted login, and the chats on blust.ch, companygraph.io and guestgraph.io then know who is asking and which models a grant lets them pick. The service belongs to blust.ch, so it runs in blust.ch's Google Cloud project, `blust-ch-mcp`, in Zurich, `europe-west6`, beside the MCP host at mcp.blust.ch and its chat, which `robertblust/mcp-blust-ch` deploys there. The project, its billing and its one budget are that repository's; what ZITADEL needs inside the project is Terraform in this one, applied by GitHub Actions.

The repository is public and holds no person, address, key or token. People and the roles granted to them live in ZITADEL and are granted in its console, because an address belongs in no repository; every secret lives in Secret Manager and reaches a service or a workflow from there.

## Infrastructure

`infra/bootstrap/` is applied by the owner, into `blust-ch-mcp` under their own login, with the state `infra/bootstrap/README.md` says how to keep, and makes what CI needs before it can authenticate: the APIs ZITADEL uses, the state bucket `id-blust-ch-tfstate`, the identity pool `id-github`, the two CI accounts and the three accounts the services run as. It makes no project, no budget and no organization policy, since those are mcp-blust-ch's, and the budget mcp-blust-ch keeps for the project covers ZITADEL too. Where a name would meet one that mcp-blust-ch makes in the project it carries `id-`: the pool, because the MCP host's is `github`, and the accounts `id-deploy` and `id-deploy-plan`, because the MCP host has a `deploy@` of its own. A run for a pull request plans as `id-deploy-plan@`, and only a push to `main` may apply, as `id-deploy@`; a run on `main` started any other way gets neither. `id-deploy-plan@` changes nothing: it reads the configuration and IAM policies of what both roots declare, both roots' state, which holds no secret that opens anything, and four secrets' values: `zitadel-admin-key`, because the `zitadel/` plan must sign in to ZITADEL to read what it holds, and that key is the instance's IAM_OWNER, so every pull request run, Dependabot's included, holds it while it runs; `zitadel-google-client-secret` and `zitadel-microsoft-client-secret`, which the same plan gives ZITADEL as write-only arguments once a Google client or an Entra ID application is named; and `zitadel-smtp-password`, the Gmail app password it gives ZITADEL the same way once the mail's account is set. The one secret in the state is the `signing_key` ZITADEL generates for the link check's Actions target, kept in the `zitadel/` state; the target's JWT payload does not use it, so a reader of the state can forge nothing the link check accepts. `id-deploy@` reads the same, writes what both roots declare, makes the secrets and sets who reads each without reading a value itself, except those four, and may grant only the Cloud SQL client role on the project. It still has two ways to any other ZITADEL secret's value, which the roles it needs cannot close: it could set a secret's policy to let itself read it, and with the Cloud Run administrator role and the service account user role on `zitadel@` it could deploy a revision that runs as ZITADEL's identity and reads that identity's secrets. Every grant and every service it makes is declared in `infra/` and recorded in the audit log, and only a push to `main`, after a reviewed merge, holds it. A pull request from a fork is refused by both plan jobs rather than skipped, so it cannot pass the required checks unplanned. `deployment.json` holds this deployment's own values, the project, its number, the region, the domain and the repository, and every root and workflow reads them from there.

`infra/` is applied by `.github/workflows/infra.yml` on every push to `main`, with its state at the `infra` prefix of the bucket, and is what runs ZITADEL: PostgreSQL 18 on Cloud SQL at its smallest shared-core tier, reached through the Cloud SQL socket; ZITADEL, its login v2 and the link check as three Cloud Run services that scale to zero; the secrets in Secret Manager; and a global load balancer with a Google-managed certificate for `id.blust.ch`, which sends `/ui/v2/login` to the login, `/link-check` to the link check and everything else to ZITADEL over HTTP/2. `infra/domain.tf` says why a load balancer and not a domain mapping. The login runs this repository's own image, `ghcr.io/robertblust/id-blust-ch-login`: ZITADEL's login at the same release with one change, in `login/Dockerfile`, which keeps the language and theme switchers under the card's right edge at every width, where ZITADEL's layout moves them to the window's edge from tablet width up. The workflow builds it on every run and pushes it on `main` before it applies, under a tag naming the release and the Dockerfile's hash; a release that no longer has the row the Dockerfile changes fails the build, and the pull request that moves `zitadel_version` shows it. The login asks every account whose address is not verified for the code it mails there, after any sign-in and before the account is used, since it runs with `EMAIL_VERIFICATION=true`; the accounts the owner makes have their address verified already. The link check is `link-check/`, a small Node service that ZITADEL calls after every sign-in with Google or Microsoft, and that links the account to the one user holding its proven address; it reads the key of the ZITADEL machine user `link-check` from `zitadel-link-check-key`, which starts as `{}`, no key, so until the owner adds one it links nobody and every sign-in goes on as it would without it. That machine user is a user manager of `blust.ch`, which holds the owner's IAM_OWNER user and `terraform`, so the key is as strong as the instance owner's, and `infra/bootstrap/README.md` says what it reaches. The workflow runs its tests, builds its image, `ghcr.io/robertblust/id-blust-ch-link-check`, and pushes it on `main` before it applies, under a tag that is a hash of every file in the folder, the same hash `infra/run.tf` computes. A first sign-in after a quiet hour waits a few seconds while the services start, which is the price of paying nothing while nobody signs in. After each apply the workflow reads `https://id.blust.ch/.well-known/openid-configuration` and fails unless its `issuer` is `https://id.blust.ch`.

ZITADEL's masterkey, the database password, the first admin's password and the login's cookie secret are generated by Terraform into Secret Manager as ephemeral values, written once as write-only arguments, so none of them is in the state or a plan; the masterkey can never change once ZITADEL has started with it, and no apply may destroy a secret. Each service's identity reads its own secrets and no other. The login's token, the key the `zitadel/` root signs in with and the link check's key exist only once ZITADEL runs, and the secrets of the Google OAuth client and of the Entra ID application only once the owner has made them at Google and at Microsoft, so Terraform makes their secrets and the owner adds their values by hand, as the steps below say. The owner's login name reaches Terraform from the repository secret `ZITADEL_ADMIN_LOGIN_NAME` and nowhere else.

`zitadel/` is applied by `.github/workflows/zitadel.yml` on every push to `main`, after `infra/` has made the instance, with its state at the `zitadel` prefix, and is what ZITADEL holds: the organizations `companygraph.io` and `guestgraph.io` beside `blust.ch`, which ZITADEL's first start made; the project `chat` in `blust.ch`, its roles `sonnet-5-5`, `opus`, `fable` and `haiku`, and its grant to the two other organizations with every role; one application per site in `sites.json`, a public client using the authorization code with PKCE, whose access tokens are JWTs that carry the roles; the instance's login, with passkeys allowed, login v2 turned on and blust.ch's colors and mark; and, once Google or Microsoft is named, the machine user `link-check` and the Actions target and execution through which ZITADEL calls the link check. Every organization inherits that login and none sets one of its own, since a login an organization sets in the console is a copy that no longer follows the instance's, and such a copy once hid the Google button on blust.ch. Its provider signs in as the machine user `terraform` with the key in `zitadel-admin-key`, read as an ephemeral value, so the key reaches neither a file nor the state. Whether anyone may open an account is the variable `open_sign_up` in `zitadel/policy.tf`, on by default, and registration, account creation by Google and Microsoft, the second factor and the password-reset link all follow it. While it is off, nobody registers and neither provider opens an account: the owner creates each person in the console with their address marked as verified and no password, and may send them an invitation from there; the person signs in with Google or Microsoft, which the link check links to that address once the provider has proved it, and may then add a passkey under their account at `https://id.blust.ch/ui/console/users/me`. The login settings still allow passwords, because ZITADEL lets a passkey sign in only where passwords may, so keeping it passwordless is the owner's: give nobody a password, and replace one that exists with a random one nobody keeps, since ZITADEL can set a password but not remove it. With no password to reset, the login hides its reset link, and no second factor can be added, since login v2 asks for one a user holds even after Google. While it is on, anyone registers at the login with a passkey or a password, Google and Microsoft open an account for a person who has none once they have seen the registration form, a password sign-in needs an authenticator app or a security key as its second factor, set up at once, while Google, Microsoft and a passkey need none, and the reset link shows. Either way a new account lands in `blust.ch` with no role until the owner grants one, and the login asks any account whose address is not verified for the code it mails there, before the account is used. ZITADEL itself links no account by address, for either provider, because login v2 would link into an account whose address was never verified, and once anyone may open an account that lets a stranger who opened one on someone else's address into the real owner's. The link check makes every such link, through the machine user `link-check`, only when the provider proved the address and exactly one account holds it with its address verified; `zitadel/link-check.tf`'s first comment says why, with its sources. No key of `link-check`'s is in this repository or the state: the owner makes it by hand, as step 29 says. ZITADEL's mail, the invitation and the code that verifies an address, is `zitadel/mail.tf`: it goes out as digital-platform's does, through Gmail's SMTP server with a Workspace account's app password, from `no-reply@blust.ch`, and only once the repository secret `ZITADEL_SMTP_USER` names the account; the app password is `zitadel-smtp-password` in Secret Manager, read as an ephemeral value and given to ZITADEL write-only. `zitadel/texts.tf` and `zitadel/texts/` hold the words of the login's pages and of both mails, in English and Swiss Standard German; the German says du, by the owner's choice and against `WRITING.md`'s Sie, so `texts/login-de.json` gives a du form for every German string of the login that addresses the reader, and a ZITADEL release that adds one shows it in Sie until it is added there. `zitadel/project.tf`'s first comment says how the roles tell the sites apart, and why a switch, `role_per_site`, builds a role per site and model instead.

Sign-in with Google is `zitadel/google.tf`, a way into an account the owner has made and, only while `open_sign_up` is on, a way to open one, which the provider never does on its own, so the person sees the registration form first. While it is off, the provider allows no account creation, so a Google account the link check links to no user ends on the login's account-not-found page. ZITADEL links no Google account to a user by itself; the link check does, when Google reports the address as verified and exactly one user holds that address with it verified, and the root's test holds both the switch and that auto-linking stays off. The provider does not update the user from Google, so the name and address stay what the account was made with. The OAuth client's id is no secret, since Google's own sign-in page shows it in its address, and is the default of `google_client_id`; while it is null, as it is until the owner has made the client, the root makes no provider and the login offers no external sign-in. The client's secret is in Secret Manager as `zitadel-google-client-secret`, read for each run as an ephemeral value and given to ZITADEL as the provider's write-only `client_secret`, so it reaches neither a file nor the state, which keeps only the provider's one-way hash of it to notice a rotation.

Sign-in with Microsoft is `zitadel/microsoft.tf`, beside Google, and opens an account only as Google's does, while `open_sign_up` is on; while it is off, a Microsoft account that is linked to no user ends on the account-not-found page. It accepts work and school accounts of any organization and personal Microsoft accounts, Microsoft's common tenant, and that is why ZITADEL never takes its address as verified: ZITADEL takes the address from Microsoft Graph, which says nothing of whether it is verified, and the administrator of any organization's directory can give a user any address, so a link on that address alone would let them sign in as whoever holds it here. The link check proves the address per sign-in instead, from Graph with the access token ZITADEL hands it: a work or school account's when its domain is one the person's own organization has verified, a personal account's by the form of its id. It links a proven address as it links Google's, and a link it refuses is made one of two ways. An invited person makes it themselves: they enter the invitation's code, which proves who they are, and choose Microsoft where the login asks how they will sign in. A person who already signs in with Google or a passkey cannot, because login v2 offers a link only after a code it mails, and it mails one only to a user with no way in yet; it tells them "User is already verified!". The owner makes that link instead, with `zitadel/link-idp.py`, as step 26 says. A person whose Microsoft address the link check cannot prove, a guest in another organization's directory among them, and who wants Microsoft alone therefore needs the invitation. The provider does not update the user from Microsoft. The application's client id is no secret and is the default of `microsoft_client_id`, null until the owner has made the application, and while it is null the login offers no Microsoft button and the invitation does not name Microsoft. The client's secret is `zitadel-microsoft-client-secret` in Secret Manager, read and given to ZITADEL write-only as Google's is. Microsoft lets a client secret live 24 months at most, so the owner renews it before it expires, as step 24 says.

The apply prints the output `sign_in`, keyed by each site's origin: the issuer, the project id, the organization whose grants count on that site and the site's client id, with the prefix of its roles when `role_per_site` is on. It is what each site's `chat.json` takes as its `sign_in` block.

## The shared project

ZITADEL shares `blust-ch-mcp` with the MCP host, and a role granted on the project reaches every resource of its kind there, whichever repository made it. So each identity's roles are held to ZITADEL's resources wherever Google lets a condition name them, and what neither can be held to is written down here, with what the MCP host's identities reach of ZITADEL. The owner accepted that trade for keeping blust.ch's services in blust.ch's project.

`id-deploy@` holds its Secret Manager role on secrets named `zitadel-*` and the Cloud SQL administrator on the instance `zitadel`, by conditions on the resource's name, and acts as `zitadel@`, `zitadel-login@` and `zitadel-link-check@` alone, by grants on those three accounts rather than on the project. What it still reaches of the MCP host: the Cloud Run administrator holds no condition, since Cloud Run takes none on a resource's name, so it could change, replace or delete the services `mcp` and `chat` and set who may invoke them, though any revision it deploys runs as one of ZITADEL's three accounts; the load balancer administrator reaches any load balancer in the project, and the MCP host has none; the project IAM administrator lets it add or remove the Cloud SQL client role for anyone, and nothing else. It can make a secret of any name, since making one is checked on the project, but administer or read none outside `zitadel-*`.

`id-deploy-plan@` holds a viewer role for each kind of resource ZITADEL uses rather than the project's viewer, which in a shared project would also read the MCP host's logs, its Firestore meter and, through each bucket's default policy, its state and the chat's reports. Its Secret Manager and Cloud SQL viewers are held to ZITADEL's by the same conditions. What it still reads of the MCP host: the configuration of the services `mcp` and `chat`, through the Cloud Run viewer, and every IAM policy in the project, through the security reviewer; it reads no value and no object of the MCP host's.

The MCP host's own identities, made by the shared bootstrap in `companygraph/mcp-server`, reach ZITADEL in turn. Its apply identity, `terraform@`, holds the project IAM administrator without a condition, the Cloud Run administrator, the service account administrator and user, and the storage administrator, so a run on `main` in `robertblust/mcp-blust-ch` can reach everything of ZITADEL's: it can grant itself any secret's value, the masterkey's included, deploy a revision as `zitadel@`, act as `id-deploy@`, and read or replace this repository's state. Its plan identity, `terraform-plan@`, which a run on any ref there may take, holds the project's viewer: it reads ZITADEL's configuration, its logs and IAM policies, the owner's login name in the service's configuration among them. It does not read this repository's state, because the bootstrap sets the state bucket's policy whole and leaves out the project's viewers, whom a new bucket's default policy lets read every object. It reads no secret's value. `firebase-adminsdk-fbsvc@`, which Firebase made for the MCP host's hosting, holds the service account token creator on the project, so whoever may act as it, `terraform@` among them, may act as any account there, ZITADEL's included. The MCP host's other accounts hold nothing of ZITADEL's. The two repositories keep separate identity pools, so no token of one becomes an identity of the other.

## The owner's steps

Some steps need the owner's hands, because they create something outside this repository or need a role CI does not hold. They are done once, in this order.

1. Create the repository on GitHub as `robertblust/id-blust-ch`, public, push `main` to it, and add a ruleset on `main` that requires the status check `conventions / conventions` and a pull request.
2. Apply `infra/bootstrap/` into `blust-ch-mcp` as its README says, under your own login, and then run the two checks it names for the network `default` and the default compute account, since the apply turns on Compute Engine in the shared project; the Owner role you hold on the project covers everything it makes. `deployment.json` already names the project, its number and the repository's GitHub id, and nothing in it waits for the bootstrap.
3. Set the owner's login name, their email address, as the secret ZITADEL's first start makes the instance's first admin from, once for Actions and once for Dependabot, whose pull requests read only Dependabot's secrets: `gh secret set ZITADEL_ADMIN_LOGIN_NAME --repo robertblust/id-blust-ch` and the same with `--app dependabot`, each reading the value from the prompt.
4. Open the state of `infra/` once, before the first plan can post, since the plan's identity may read the state but never create it: `terraform -chdir=infra init`, run locally under the owner's login on the pull request's branch, creates the empty state at the `infra` prefix. Then add `infra / terraform` to the ruleset's required checks.
5. Merge, by name. The first apply makes everything and then fails at its live check by design, because `id.blust.ch` has no DNS record yet. Run `terraform -chdir=infra output dns_records` and add the A record it names at Hostpoint, where blust.ch's records are kept. Google issues the certificate once the record resolves, which can take an hour; re-run the failed job then, and it passes when the discovery document names `https://id.blust.ch` as its issuer.
6. Sign in as the first admin at `https://id.blust.ch/ui/console`, with the login name of step 3 and the password from `gcloud secrets versions access latest --secret zitadel-admin-password --project blust-ch-mcp | pbcopy`, and set a password of your own and a passkey when ZITADEL asks. This is ZITADEL's built-in login, which serves until the `zitadel/` root turns login v2 on.
7. Make the login's own user. In the console, under Users, Service Users, create `login-client`, named Login client; under its Personal Access Tokens create one and copy it; and under the instance's settings, Members, add `login-client` with the role Instance Login Client, `IAM_LOGIN_CLIENT`. Add the token as the next version of `zitadel-login-token`, on stdin: `read -rs T && printf %s "$T" | gcloud secrets versions add zitadel-login-token --data-file=- --project blust-ch-mcp; unset T`, pasting the token at the silent prompt. A login instance started after that reads it; one already running keeps the placeholder until it scales to zero, within a quarter of an hour without traffic.
8. Make the user the `zitadel/` root signs in as. In the console create the service user `terraform` and add it under the instance's Members with the role Instance Owner, `IAM_OWNER`. The console only downloads a JSON key as a file, so the key is made through the API instead, straight into Secret Manager: create a personal access token for `terraform` that expires tomorrow, copy it and the user's id, then run `read -rs PAT && curl -fsS -X POST -H "Authorization: Bearer $PAT" -H 'content-type: application/json' -d '{"type":"KEY_TYPE_JSON","expirationDate":"2027-10-22T00:00:00Z"}' https://id.blust.ch/management/v1/users/<terraform user id>/keys | jq -r .keyDetails | base64 --decode | gcloud secrets versions add zitadel-admin-key --data-file=- --project blust-ch-mcp; unset PAT`, and delete the token in the console. The key's expiry is a date the owner chooses and renews the same way.
9. Open the state of `zitadel/` once, the same way as `infra/`'s in step 4, with `terraform -chdir=zitadel init` on the pull request's branch, and add `zitadel / terraform` to the ruleset's required checks. Its plan can pass only once steps 6 to 8 are done.
10. Merge, by name. The apply turns login v2 on and prints `sign_in`, which `terraform -chdir=zitadel output -json sign_in` repeats.
11. Confirm in the Anthropic Console that the workspace the chats use allows all five models, and that the organization's data retention allows Claude Fable 5.1.
12. Grant your own user every role on all three sites, in the console. In `blust.ch`, under the project `chat`, Authorizations, add your user with all four roles. In `companygraph.io` and in `guestgraph.io`, under Granted Projects, `chat`, Authorizations, add your user, whose home is `blust.ch`, with all four roles. This is the try of the grant model: if a site's organization cannot name a user of `blust.ch`, or the token of step 13 lacks that organization's id beside a role, set `role_per_site`'s default to `true` in `zitadel/project.tf` in a pull request, merge it, and grant the roles of the form `companygraph-io-opus` in `blust.ch` instead; each site's `chat.json` then carries the `role_prefix` that `sign_in` names.
13. Check one token by hand, through the blust.ch application, before blust.ch's pages carry the sign-in, since the panel would otherwise take the code first. Make a PKCE pair with `V=$(openssl rand -hex 32); C=$(printf %s "$V" | openssl dgst -sha256 -binary | openssl base64 -A | tr '+/' '-_' | tr -d '=')`, run `open "https://id.blust.ch/oauth/v2/authorize?client_id=<client_id>&redirect_uri=https%3A%2F%2Fblust.ch%2F&response_type=code&scope=openid%20profile%20urn%3Azitadel%3Aiam%3Aorg%3Aproject%3Aid%3A<project_id>%3Aaud%20urn%3Azitadel%3Aiam%3Aorg%3Aprojects%3Aroles&code_challenge=$C&code_challenge_method=S256"` in the same shell, so `$C` expands, with the `client_id` and `project_id` of `sign_in`'s `https://blust.ch` entry, sign in, and take the `code` from the address blust.ch is opened at. Then `curl -fsS https://id.blust.ch/oauth/v2/token -d grant_type=authorization_code -d client_id=<client_id> -d redirect_uri=https://blust.ch/ -d code_verifier="$V" -d code=<code> | jq -r .access_token | cut -d. -f2 | tr '_-' '/+' | jq -R '@base64d | fromjson'` prints the token's claims and never the token: `iss` is `https://id.blust.ch`, `aud` holds the project id, and `urn:zitadel:iam:org:project:roles` holds each granted role with the organization id of each site it was granted on.
14. Make Google's consent screen, in the Google Cloud console for `blust-ch-mcp`, under Google Auth Platform. Under Branding, name the app `id.blust.ch`, give your address as the user support email and the developer contact, link blust.ch's home page and privacy page, and add `blust.ch` as an authorized domain; add no logo, since a logo makes Google verify the brand before the screen may show it. Under Audience, choose External and then Publish app, so the app is In production and any Google account may sign in, not only listed test users. Under Data Access, add the scopes `openid`, `.../auth/userinfo.email` and `.../auth/userinfo.profile`, the three ZITADEL asks for; they are not sensitive, and Google asks for its verification only for sensitive or restricted scopes (https://support.google.com/cloud/answer/7454865, read Oct 25, 2026).
15. Make the client. Under Clients, Create client, choose Web application, name it `ZITADEL`, and add one authorized redirect URI, `https://id.blust.ch/idps/callback`. That is login v2's callback, which this instance uses; ZITADEL's documentation for v4 says "V2 uses `https://${CUSTOM_DOMAIN}/idps/callback`, while V1 uses `https://${CUSTOM_DOMAIN}/ui/login/login/externalidp/callback`" (https://zitadel.com/docs/guides/integrate/login-ui/external-login, read Oct 25, 2026), and the load balancer sends it to ZITADEL. Google shows the client's secret once, when the client is made, so keep the dialog open for the next step.
16. Put the client's secret into Secret Manager, on stdin: `read -rs S && printf %s "$S" | gcloud secrets versions add zitadel-google-client-secret --data-file=- --project blust-ch-mcp; unset S`, pasting the secret at the silent prompt. The secret exists once the pull request that made `zitadel/google.tf` has merged and `infra/` has applied.
17. Name the client, by setting `google_client_id`'s `default` in `zitadel/google.tf` from `null` to the client's id, the one ending in `.apps.googleusercontent.com`, in a pull request. Its `zitadel / terraform` plan adds the Google provider and changes the default login policy to allow external sign-in with that provider alone, and nothing else. Merge, by name. The login at `https://id.blust.ch` then shows a Google button on the page that asks for the login name. A person you have invited signs in with it using a Google account whose verified address is the address you gave their user in the console: the first time, once step 29 has given the link check its key, the link check links the two and the login signs them in, and later sign-ins with Google find the link. A Google account with any other address ends on the login's account-not-found page, and while `open_sign_up` is off no account is made.
18. Make the login's image public, once, after the first push to `main` that builds it, since Cloud Run pulls it without signing in to GitHub and a package that Actions pushes first can be private: on GitHub, under your Packages, `id-blust-ch-login`, Package settings, Change visibility, Public. Then re-run the failed `infra / terraform` job, which deploys it. The repository is public, so the image shows nothing the repository does not.
19. Give ZITADEL's mail the app password, once the pull request that made `zitadel/mail.tf` has merged and `infra/` has applied, which makes the empty secret. It is the one digital-platform's ZITADEL signs in with, copied on the machine and never shown: `gcloud secrets versions access latest --secret zitadel-smtp-password --project dp-reference | gcloud secrets versions add zitadel-smtp-password --data-file=- --project blust-ch-mcp`. A rotation at Google then needs a new version in both projects.
20. Let the account send as `no-reply@blust.ch`: make the address an alias of the account in the Google Admin console if blust.ch is a domain of the account's Workspace, and add it in the account's Gmail under Settings, Accounts, Send mail as. Without it, Gmail sends ZITADEL's mail from the account's own address.
21. Name the account, its address, as the repository secret `ZITADEL_SMTP_USER`, once for Actions and once for Dependabot, as in step 3: `gh secret set ZITADEL_SMTP_USER --repo robertblust/id-blust-ch` and the same with `--app dependabot`. Then re-run the last `zitadel / terraform` run on `main`; its apply adds the Gmail provider and makes it active. Test it in the console, under the instance's settings, SMTP provider, which sends a test mail to an address you give.
22. Make the application, in the Microsoft Entra admin center at `https://entra.microsoft.com`, signed in to your own tenant, under App registrations, New registration.
