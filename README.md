# id.blust.ch

The family's own identity service, ZITADEL, at `https://id.blust.ch`. A reader signs in there once, on its hosted login, and the chats on blust.ch, companygraph.io and guestgraph.io then know who is asking and which models a grant lets them pick. The service runs in a Google Cloud project of its own in Zurich, `europe-west6`, and everything below the project is Terraform applied by GitHub Actions.

The repository is public and holds no person, address, key or token. People and the roles granted to them live in ZITADEL and are granted in its console, because an address belongs in no repository; every secret lives in Secret Manager and reaches a service or a workflow from there.

## Infrastructure

`infra/bootstrap/` is applied by the owner, with the state `infra/bootstrap/README.md` says how to keep, and makes what CI needs before it can authenticate: the project, its APIs, the state bucket, the identity pool and the two service accounts, and the monthly budget. A pull request plans as `deploy-plan@`, which reads and changes nothing, and only a run on `main` may apply, as `deploy@`. `deployment.json` holds this deployment's own values, and every root and workflow reads them from there.

`infra/` is applied by `.github/workflows/infra.yml` on every push to `main`, with its state at the `infra` prefix of the bucket, and is what runs ZITADEL: PostgreSQL 18 on Cloud SQL at its smallest shared-core tier, reached through the Cloud SQL socket; ZITADEL and its login v2 as two Cloud Run services that scale to zero; the secrets in Secret Manager; and a global load balancer with a Google-managed certificate for `id.blust.ch`, which sends `/ui/v2/login` to the login and everything else to ZITADEL over HTTP/2. `infra/domain.tf` says why a load balancer and not a domain mapping. A first sign-in after a quiet hour waits a few seconds while the services start, which is the price of paying nothing while nobody signs in. After each apply the workflow reads `https://id.blust.ch/.well-known/openid-configuration` and fails unless its `issuer` is `https://id.blust.ch`.

ZITADEL's masterkey, the database password, the first admin's password and the login's cookie secret are generated by Terraform into Secret Manager; the masterkey can never change once ZITADEL has started with it. The login's token and the key the `zitadel/` root signs in with exist only once ZITADEL runs, so Terraform makes their secrets and the owner adds their values by hand, as the steps below say. The owner's login name reaches Terraform from the repository secret `ZITADEL_ADMIN_LOGIN_NAME` and nowhere else.

## The owner's steps

Some steps need the owner's hands, because they create something outside this repository or need a role CI does not hold. They are done once, in this order.

1. Create the repository on GitHub as `robertblust/id-blust-ch`, public, push `main` to it, and add a ruleset on `main` that requires the status check `conventions / conventions` and a pull request.
2. Fill the two placeholders `deployment.json` holds before the bootstrap can run: `repository_id`, from `gh api repos/robertblust/id-blust-ch --jq .id`, and `budget_chf`, the monthly figure in whole francs.
3. Apply `infra/bootstrap/` as its README says, and write the `project_number` it prints into `deployment.json`. The three values reach `main` in one pull request.
4. Set the owner's login name, their email address, as the secret ZITADEL's first start makes the instance's first admin from, once for Actions and once for Dependabot, whose pull requests read only Dependabot's secrets: `gh secret set ZITADEL_ADMIN_LOGIN_NAME --repo robertblust/id-blust-ch` and the same with `--app dependabot`, each reading the value from the prompt.
5. Open the state of `infra/` once, before the first plan can post, since the plan's identity may read the state but never create it: `terraform -chdir=infra init`, run locally under the owner's login on the pull request's branch, creates the empty state at the `infra` prefix. Then add `infra / terraform` to the ruleset's required checks.
6. Merge, by name. The first apply makes everything and then fails at its live check by design, because `id.blust.ch` has no DNS record yet. Run `terraform -chdir=infra output dns_records` and add the A record it names at Hostpoint, where blust.ch's records are kept. Google issues the certificate once the record resolves, which can take an hour; re-run the failed job then, and it passes when the discovery document names `https://id.blust.ch` as its issuer.
7. Sign in as the first admin at `https://id.blust.ch/ui/console`, with the login name of step 4 and the password from `gcloud secrets versions access latest --secret zitadel-admin-password --project id-blust-ch | pbcopy`, and set a password of your own and a passkey when ZITADEL asks. This is ZITADEL's built-in login, which serves until the `zitadel/` root turns login v2 on.
8. Make the login's own user. In the console, under Users, Service Users, create `login-client`, named Login client; under its Personal Access Tokens create one and copy it; and under the instance's settings, Members, add `login-client` with the role Instance Login Client, `IAM_LOGIN_CLIENT`. Add the token as the next version of `zitadel-login-token`, on stdin: `read -rs T && printf %s "$T" | gcloud secrets versions add zitadel-login-token --data-file=- --project id-blust-ch; unset T`, pasting the token at the silent prompt. A login instance started after that reads it; one already running keeps the placeholder until it scales to zero, within a quarter of an hour without traffic.
9. Make the user the `zitadel/` root signs in as. In the console create the service user `terraform` and add it under the instance's Members with the role Instance Owner, `IAM_OWNER`. The console only downloads a JSON key as a file, so the key is made through the API instead, straight into Secret Manager: create a personal access token for `terraform` that expires tomorrow, copy it and the user's id, then run `read -rs PAT && curl -fsS -X POST -H "Authorization: Bearer $PAT" -H 'content-type: application/json' -d '{"type":"KEY_TYPE_JSON","expirationDate":"2027-10-22T00:00:00Z"}' https://id.blust.ch/management/v1/users/<terraform user id>/keys | jq -r .keyDetails | base64 --decode | gcloud secrets versions add zitadel-admin-key --data-file=- --project id-blust-ch; unset PAT`, and delete the token in the console. The key's expiry is a date the owner chooses and renews the same way.
